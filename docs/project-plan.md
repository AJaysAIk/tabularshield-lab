# Project management evidence and next-stage plan

This is a worked planning artifact for the prototype and a proposed progression. It is **not** a claim of having managed an actual funded KTP or a client steering committee.

## Prototype acceptance criteria

- Public input provenance, appropriate licences, immutable snapshots and contributor units documented.
- All seven comparators evaluated on the fixed workload; failed defenses retained.
- Repeated-query and exact-margin attacks produce measurable, interpretable outcomes.
- Geographic experiment uses real coordinates with explicit aggregation limitations.
- API boundary and numerical invariants verified; full rerun matches reference evidence.
- A non-specialist can read the report, and a technical reviewer can reproduce the experiment.

## Proposed progression through six research stages

| Stage | Next deliverable | Acceptance / decision | Dependency |
|---|---|---|---|
| Exploration | Focused literature map and host-specific threat model | Domain and business owners agree protected unit, queries and intended users | Stakeholder access |
| Risk/utility framework | Policy, attack suite and utility tolerances | Review considers linked tables and adversary knowledge, not one proxy | Domain review |
| Method development, including geography | Calibrated alternatives and controlled ablations | Reproducible improvement under agreed criteria, or explicit negative result | Authorized representative data |
| Empirical validation | Cross-dataset and use-case report | Holdout designs and disclosure review agreed before evaluation | Data agreements |
| Integration | Versioned host adapter, contract tests and operational controls | Host team's code review, correctness and deployment checks pass | Platform interfaces |
| Benefits and close | Supported operating guide, transfer session and benefits evaluation | Users can maintain the approved workflow; sponsor approves closure | Actual deployment evidence |

## Three-month rolling planning pattern

Maintain a weekly delivery log and risk register. Plan the next two weeks in detail, the following month by milestones, and the next quarter by dependencies and decisions. Report scope changes early rather than hiding them behind optimistic deadlines. This template must be adapted with real supervisors and company staff.

## Risks and decisions

| Risk | Early signal | Response / decision owner |
|---|---|---|
| Data or platform access delayed | First agreed deadline missed | Supervisor/company owner: sequence public-data work while resolving access |
| Metric gives false reassurance | Attack succeeds despite low direct proxy | Statistical lead: revise threat model and acceptance criteria |
| Protection destroys utility | Required analyses no longer usable | User/domain owner: reconsider granularity, method or permitted outputs |
| Scope expands into many query types | No stable evaluation contract | Project board: prioritize a release workload and defer extras |
| Knowledge concentrated in one developer | Colleague cannot reproduce run | Pair walkthrough, documented decisions and observed handover exercise |

## Development budget illustration — not expenditure

If a £4,000 development budget is available, a starting proposal could reserve £1,400 for statistical-disclosure training, £800 for research communication, £800 for a relevant workshop, £600 for specialist mentoring and £400 contingency. Obtain actual quotations, eligibility and supervisor approval before commitment. Mandatory management training and travel should not be assumed to come from the same budget without checking project rules. No spending, attendance or approval is claimed here.

## Training artifact

Use the learning guide for a 45-minute walkthrough: purpose and threat model (10 min), run a query (10), recover a suppressed value (10), compare utility (10), explain limitations and ask for a repeat demonstration (5). This is a prepared lesson plan; delivery and participant competence would need separate evidence.
